Создать заказ 
→ зарезервировать товар на складе 
→ Создать одну заявку в снабжение
→ Создать один заказ поставщику 
→ Выполнить заказ поставщику
→ Завершить заявку в снабжение
→ Изменить статус заказа на  in_production

Изучаем события, consumer groups, partitions и порядок сообщений.

## Уточнённый сценарий

Заказ на 10 изделий; 5 готовых изделий уже есть на складе.
Для каждого из оставшихся 5 нужен один материал A, один B и один C.
На складе есть по 5 единиц A и B, материала C нет.

1. Создать заказ: событие `order.created`.
2. Зарезервировать 5 готовых изделий и по 5 материалов A/B.
   Сохранить план производства 5 изделий и дефицит C: `warehouse.reserved`.
3. Создать одну заявку только на 5 единиц C: `supply.request_created`.
4. Создать один заказ поставщику: `supply.order_created`.
5. Зафиксировать выполнение поставщиком: `supply.order_completed`.
6. Принять C и зарезервировать его для заказа: `warehouse.supply_received`.
7. Завершить заявку: `supply.request_completed`.
8. Перевести клиентский заказ в `in_production`: `order.in_production`.

Если C уже есть частично, закупается только недостающее количество.
Если все материалы доступны, шаги снабжения пропускаются.
Если все готовые изделия есть на складе, заказ готов (`producted`)
без производства и закупки: событие `order.ready`.

## Границы и доставка событий

Оркестратор: `app/src/Modules/Saga/Application/ProductionSaga.php`.
Он вызывает только публичные Application API модулей.
Состояние процесса восстанавливается из заказа, сохранённого плана резерва,
заявки/заказа поставщику и inbox; отдельной таблицы состояний saga пока нет.

Изменение агрегата через ORM и запись `shared.outbox` атомарны. Relay отправляет
события в Kafka после commit, ожидает delivery report, затем отмечает публикацию.
При сбое между публикацией и отметкой событие может прийти повторно;
inbox потребителя (`saga.inbox`) обеспечивает дедупликацию по `(consumer, event_id)`.
Inbox, обработка события и новые события outbox коммитятся одной транзакцией;
Kafka offset фиксируется после неё. При ошибке worker завершает работу
без commit offset; после устранения причины его нужно перезапустить.
Автоматический DLQ и бизнес-компенсации пока не реализованы.

Топик: `saga.events`, 3 партиции. Ключ всех событий заказа — `order:<id>`;
порядок гарантируется в одной партиции. Число партиций этого топика
не меняют во время выполняющихся saga: при изменении ключ может попасть
в другую партицию. Одинаковая consumer group (`KAFKA_CONSUMER_GROUP`,
по умолчанию `saga-app`) распределяет партиции между экземплярами worker.
Другую group используйте для наблюдения, а не для повторного запуска
того же оркестратора: она получит все события независимо.

Запуск учебного примера описан в корневом `readme.md`.
